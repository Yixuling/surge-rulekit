# rule-audit

## 要解决的问题

`[Rule]` 末尾是 LAN、ASN.China 两条 IP 规则。没被任何域名规则点名的请求，必须先在本地解析出 IP 才能判断是否国内，判断完多数仍落到 FINAL 走代理——这次解析白等几十到上百毫秒，还把域名交给了本地 DNS（即所谓 DNS 泄露）。给常用的境外服务点名，就能直接走代理、跳过这一步。

## 1. 列名单

```
bun run audit
```

只读，结果只打印：数据覆盖天数、落到 FINAL 的域名（先列能在最近请求里对上发起应用的，按应用分组；其余按字母排）、经 ASN.China 直连的数量。

名单**不按流量排序，也不要自己去读流量排序**。Surge 按域名的流量统计在界面和 CLI 里都会乱跳（空闲域名也会在几 KB 与几十 MB 间变动，多次读取取最大值也不收敛），按它排序曾让几乎不用的站点排到前面、误导判断。可靠的只有三样：本月出现过哪些域名、`rule match` 算出的命中规则、最近请求里的发起应用。Surge 也不记录访问次数，所以"常用与否"交给用户判断；不要为了得到频率去后台持续记录请求，那等于在磁盘上积累访问记录。

读名单时还要知道：

- 只有当月数据（按域名不保留上月），月初跑名单会很短
- 发起应用只覆盖最近约 200 条请求，对不上不代表不常用；要查某应用实际连哪些主机，用 `surge-cli --raw dump active`（或 `recent`）按 `processPath` 过滤
- 统计与 `rule match` 都按主域名算，只收录了子域名的规则可能判断偏差
- `curl` 之类出现在发起应用里，多半是之前测速留下的，不算用户使用；AdGuard 做 HTTPS 过滤时会代发浏览器等应用的请求，发起应用显示为它的 network-extension，实际来源看不出
- ASN.China 那组不用处理：直连本就要本地解析，点名也省不了

## 2. 先替用户筛，再给分类建议

名单动辄几百上千个域名，原样丢给用户没法看。先自己筛一遍，只把值得用户花时间的部分摆出来。判断"是否常用"依据三样：

1. **本机装了什么**：`ls /Applications /Applications/Setapp ~/Applications`、`brew list --cask`、`brew leaves`、`mise ls --current`。已安装应用的官方域名（含更新、同步、插件市场，如 Raycast 的 `raycast-releases.com`、Cursor 的 `open-vsx.org`）是最可靠的候选
2. **是否主流**：大家都在用的境外服务与开发者文档站，可以作为次一级候选；认不出的不猜
3. **记忆**：用户以前否决过的不再推荐；用户的工作领域（如常用的语言栈）有助于判断哪些文档站常看

摆给用户时，第一组放已安装应用的域名（按应用列出），其余各组只列条目，`.invalid` 之类的测试域名和认不出的长尾只报个数。

分类只是给用户的建议，每一条都要用户确认才落地——规则改错的代价是某个服务突然变慢或打不开，而且往往过一阵才被发现。用户否决的条目记进 Claude 的项目记忆（不进仓库），下次别再推荐。

| 类别 | 给用户的建议 |
|---|---|
| 主流境外服务（开发工具、生产力应用） | 加入公开的 `rules/GlobalExtra.list`，可整组确认 |
| AI 相关 | 不给默认去向。用户的 AI 组走专线节点，哪些服务该走专线只有用户知道；只提供所属服务、当前命中规则、发起应用，由用户选 `rules/AI.list`、GlobalExtra 或不处理 |
| 机场、中转 CDN、灰色服务、带隐私的域名 | 不给默认去向，标注"只能私有"：公开仓库不得出现这类域名（见 AGENTS.md 脱敏）；用户要加才写进 `private/snippets/private-rules.conf` |
| 属于有自维护列表的服务组（如 JetBrains） | 补进对应列表（`rules/JetBrains.list`），让它跟着服务组的出口走；放进 GlobalExtra 会绕过服务组的选择 |
| 有服务组但无自维护列表、或大流量下载的（如 Steam） | 不给默认去向：点名可能让大流量下载改走机场 |
| 纯追踪（见下） | 建议加入 `rules/Guard.list` |
| 带功能的追踪（跳转、风控、表单，见下） | 不收，也不放行处理，维持现状 |
| 测试域名、国内开发者个人站、偶尔访问的长尾 | 不处理，偶尔解析一次的代价可以忽略 |

认不出一个域名属于什么服务时，直说认不出，别猜——猜错会把它放进错误的类别。

### Guard.list 的收录标准

`Guard.list` 是用户自己启用的拦截列表，和模板里注释掉的上游三条（Advertising、Privacy、Hijacking）是两回事：上游那几条公开出来只作参考，用户不打算启用（大列表常驻会挤占 iOS 网络扩展内存，隐私列表误拦多）；`Guard.list` 小而可控，出了问题能定位到具体一条。所以它不必回避和上游重复，标准只看是否"在用户这台电脑上确认过"：

1. 在本机流量里实际出现过（由 `bun run audit` 捕捉，不凭印象加）
2. 是纯追踪：只在后台上报行为，页面和应用的功能不依赖它的返回（如 Hotjar、Mixpanel、PostHog、HubSpot 的追踪脚本）
3. 启用后观察几天没出问题；出了问题删掉那一条

很多追踪服务同时在干活，拦掉追踪的同时功能也停了，而且问题往往过几天才在某个场景冒出来、很难联想到规则。这几类不收：

- **跳转**：链接或资源先经它记一笔再跳到真实地址，拦了就到不了目的地。营销邮件的点击追踪（Customer.io、Sailthru、Iterable 等，连"确认邮箱"链接都可能点不开）、播客音频前缀（Podtrac）、推荐链接（PartnerStack）
- **风控**：网站靠它判断是不是真人、是不是本人。设备指纹（FingerprintJS，拦了登录频繁验证、支付被拒）、反爬验证（HUMAN/PerimeterX，拦了无限弹验证或直接拒访）
- **表单与页面托管**：内容本身放在它那里。Marketo 托管的表单与落地页

拿不准一个服务属于哪类时，归到"带功能"、不收——漏拦一个追踪只是多一次上报，误拦一个功能是用户摸不着头脑的故障。

## 3. 可选：直连还是代理更快

```
bun run audit --speed 主机...
```

直连绑定物理网卡（默认 en0，`AUDIT_IFACE` 可改）绕过 Surge，代理经本机 HTTP 端口按规则出站，各测 4 次取首字节中位数。测速请求本身会进入 Surge 的请求记录，所以先列名单再测速。

解读时注意：

- 一个应用的所有主机都要测。同一应用的不同主机结论可能相反（实测 Typeless 的 API 直连快、静态资源代理快一倍），只要有一个直连不通（实测 Spark 的后端），就不能整体直连
- 早上国际出口空闲，直连常显得更快；晚高峰（20–23 点）的结果才作数。拿不准时保持走代理——它就是落到 FINAL 时的现状，不会变差

## 4. 落地

1. 把用户确认的条目写进目标文件，一律写 `DOMAIN-SUFFIX, 域名`：`rules/GlobalExtra.list` 每个应用或服务一个分组、标题只写名字；`AI.list`、`JetBrains.list` 放进对应服务的分组；`Guard.list` 按追踪类型分组；私有条目写进 `private/snippets/private-rules.conf`
2. `bun run render`、`bun test`、`surge-cli -c dist/Surge.conf`
3. 提交并推送公开文件——Surge 从 raw URL 拉 `rules/`，没推送就部署会拉不到
4. `bun run deploy` 前征得用户同意（它会改写 Mac 与 iOS 共用的运行配置）；部署后 `surge-cli external-resource update all`，再用 `surge-cli rule match <域名>` 确认不再落到 FINAL
5. 改过 `private/` 就提醒用户 `bun run private:backup`

名单本身是访问记录：不要写进仓库、提交信息或临时文件；万一写了临时文件，结束前删掉。
